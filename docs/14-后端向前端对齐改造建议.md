# 后端向前端对齐的改造建议

> 前提：**前端《终场前的一张票》是产品口径**——15 个节点、13 个二选一 + 2 个自由回答（N03、N15）、16 个 E01–E16 结局、现有美术与 UI 都保留。
> 目标：后端从“线性 15 步 + 七维 + R/P 结局”改成“**图结构 + 会话 + E 结局 + 前端同款评分**”，成为前端可调用的权威服务。
> 关联文件：[13-前后端对接差距清单.md](13-前后端对接差距清单.md)

---

## 0. 一句话建议

**不要让前端去适配后端的 N01–N15/七维/R 结局；把后端剧情层重写成前端 `story.js` 的图结构和 E01–E16 结局。**

现有后端仍然可以复用：HTTP 服务骨架、session/错误码/敏感信息拦截、确定性边界、校验脚本的思路。**需要重写的是：剧情配置格式、推进规则、结局路由、评分/徽章、review 输出、校验器。**

分两步走：

1. **先做兼容层（1–2 天）**：后端补 `/api/free-answer`、`/api/result` + CORS，让现有前端只加一行 adapter 就能跑；
2. **再做正式的图引擎（3–5 天）**：后端掌握完整路径、提前结局、自由回答确认、E 结局文案和权威评分；前端再切到统一契约。

---

## 1. 先冻结“权威口径”

在改代码前，先把下面 6 件事定死，否则会边改边返工：

| 项目 | 建议口径 | 原因 |
|---|---|---|
| 剧情节点 | 前端 `src/story.js` 的 `S`（15 个节点） | 现有 UI/美术/文案已经按它做 |
| 结局 | 前端 `E01–E16` | 前端已写 16 段文案、评级、点评；不要映射到 R/P |
| 自由回答 | N03、N15 | 前端 `free: true`；不要沿用 N12–N14 |
| 固定选项跳转 | 每个选项的 `next` 或 `ending`（按前端 `choose()`） | 后端线性 `next` 无法表达分支/提前结局 |
| 评分/徽章 | 前端 `scoreFor`/`badgesFor` 的规则，后端重算并返回 | 前端已有“后端评分”展示位；不要同时显示七维分 |
| 金额字段 | `ticket_paid`、`second_paid`、`shop_paid`、`invest_paid`，后端按选项累计 | 对齐前端 `ticketPaid/secondPaid/smallPaid/investPaid`，避免再出现 `ticket_loss/shop_loss/recovery_loss` 三套 |

> 七维评分如果评审需要，可以作为**复盘页的“风险明细”**保留，但**不能再决定结局和主分**；否则又回到两套规则打架。

```js
// game.js 现有逻辑
if (current===5 && to===7 && state.verifiedOfficial) to = 'E15';
if (current===7 && to==='E04' && state.verifiedOfficial && state.ticketPaid) to = 'E15';
```

这两条是“同一选项因历史不同而落到不同结局”的典型，后端要支持**带条件的 option target**，或单独的规则表。

## 3. 配置格式：从“线性 next”改成“图”

### 3.1 建议的新节点格式

```json
{
  "id": "N03",
  "act": "A1",
  "time": "10月27日 · 稍后",
  "title": "独立核实",
  "scene": "林夏没有拨打陌生人提供的号码，而是自行找到剧院总机……",
  "lines": [
    {"speaker": "剧院总机", "text": "员工赠票凭票入场，不存在 900 元补差流程。"}
  ],
  "prompt": "自由回答：你现在如何处理这个陌生联系人？",
  "free": true,
  "presentation": {"bg": "C", "person": "alert", "speaker": "剧院总机", "phone": [], "prop": null},
  "options": []
}
```

固定选项节点：

```json
{
  "id": "N04",
  "title": "看似正规的证件",
  "free": false,
  "options": [
    {"id": "A", "text": "相信证件照片，模拟支付 900 元", "response": "……", "next": "N05", "increments": {"ticket_paid": 900}},
    {"id": "B", "text": "拒绝向个人收款码付款，独立核实", "response": "……", "ending": "E02"}
  ]
}
```

关键变化：

- `next`/`ending` 挂在**选项**上，不再固定在节点上；
- `next` 可以是 `Nxx` 或 `Exx`；
- 支持 `conditions`/`conditional_next` 处理 E15/E16；
- `increments` 用金额字段，由后端累计；
- `presentation` 可选，给前端立绘/背景/手机/道具；前端也可以保留本地映射，但后端最好提供，避免两边漂移。

### 3.2 结局格式

```json
{
  "id": "E01",
  "title": "官方核实，骗局识破",
  "rating": "优秀",
  "narration": "剧院总机确认员工赠票没有补差款……",
  "note": "独立核验让他没有把部分真实信息误认成可信身份。",
  "score_floor": 82
}
```

- 16 条 E 结局全部写入；
- `rating` 用前端现有“优秀/良好/警告/高风险/完美/警示”；
- `score` 由后端按路径算，不由前端传；
- `review` 返回标题、评级、旁白、点评、分数、徽章，前端直接渲染。

### 3.3 自由回答规则

建议单独一张表，而不是硬编码在 `sessions.py`：

```json
{
  "N03": {
    "E01": ["官方", "总机", "剧院", "核实", "不转", "拒绝", "拉黑"],
    "N04": ["继续", "解释", "加微信", "听听", "联系对方"]
  },
  "N15": {
    "E11": ["官方", "剧院", "核实身份", "联系小岚"],
    "E12": ["举报", "报案", "银行", "止付", "保存证据"],
    "E13": ["删除", "删掉", "清空", "不处理"],
    "E14": ["分享", "提醒朋友", "告诉朋友", "传播"]
  }
}
```

- 命中唯一目标 → 返回 `target`；
- 命中多个/不确定 → 返回 `need_confirm`，前端弹确认卡；
- 敏感信息（手机号/身份证/银行卡）继续拦截；
- N03 命中 E01 时直接提前结束，不要求走完 15 步。

**匹配顺序要对齐前端 `freeRoute`：** N15 是“删除→E13、分享→E14、举报/保存证据→E12、官方核实→E11”，不是按关键词表随便优先；N03 是“官方核实且没有继续联系→E01；否则继续听→N04”。如果一段话同时命中多个意图，后端应返回 `need_confirm`，不要私自挑一个。

## 4. 引擎改造点

### 4.1 推进

`apply_choice()` 不再只写 flags，还要返回 `next`/`ending`：

```python
def apply_choice(flags, node_id, option_id, config=None):
    ...
    target = resolve_option_target(node_id, option_id, flags)
    # target 可能是 Nxx / Exx / 条件目标
    return {"flags": updated, "target": target}
```

- 目标为 `Exx` → 会话立即 `finished`，生成 review；
- 目标为 `Nxx` → `current_node = target`；
- 没有任何“必须走完 15 步”的约束；
- `build_review()` 不再检查 `n11_seen`，也不要求 N08/N12/N13 都存在。

### 4.2 结局路由

- 以选项/条件目标为主，不再用七维最低维度路由；
- `route_ending()` 可以保留为“从 flags 辅助判定”的工具，但主路径是图边；
- E15/E16 的条件规则单独测试。

### 4.3 评分/徽章

把前端 `game.js` 的两段逻辑原样搬到后端（用后端记录的 history 重算）：

```text
score = 100 - min(50, round(total_paid / 100))
if ending in {E03, E10, E16}: score -= 18
if ending == E13: score -= 15
if ending in {E01, E02, E05, E11, E12, E14}: score = max(score, 82)
score = clamp(score, 10, 100)
```

徽章：

- 独立核验：`verified_official` 或 E01/E02/E05/E11；
- 及时刹车：`stopped` 或 E04/E07/E08/E09/E12/E14/E15；
- 识别代价：发生过任意模拟付款；
- 线索保管员：E12/E14；
- 安全传递者：E14。

> 建议把这些规则放进后端独立模块 `game/scoring.py`，并写单元测试与前端 `scoreFor` 对照。不要让前端继续传 `score`。

### 4.4 金额/状态

统一为：

```text
ticket_paid   票务补差
second_paid   第二笔 900
shop_paid     128 + 188 山货
invest_paid   3000 投资/追加
total_paid    = 四项之和
verified_official / stopped / identity_confirmed
```

这些全部由后端根据选项 `increments`/`flags` 累计；前端只用于展示，不再作为权威输入。

> 两个金额特例要单独处理：前端在 **E03** 时把 `secondPaid` 直接设为 `3000 - ticketPaid`（表示累计 3000）；**E10/E16** 的旁白是累计 5000，但前端中间没有逐笔加总。后端不要照抄中间字段，建议在进入 E03/E10/E16 时按结局固定总额（3000/5000）生成 `total_paid`，否则分数和旁白会对不上。

### 4.5 变体

前端没有“变体”概念。后端现有 23 条变体建议**先删掉/归档**；如果确实需要按状态改文案，再作为可选的 `lines/scene` 覆盖，但不要影响图推进。

## 5. API 契约：两种做法，先做兼容层

### 5.1 最小兼容层（推荐先做，1–2 天）

不改前端剧情和本地跳转，只让前端 adapter 能工作：

```http
POST /api/free-answer
{ node_id: "N03", text: "...", history: [...], state: {...} }
-> { "target": "E01" } 或 { "target": 4 }
```

```http
POST /api/result
{ ending_id: "E12", score: 82, history: [...], state: {...} }
-> { "ending_id": "E12", "score": 91, "badges": ["独立核验", "..."] }
```

实现要点：

- 复用前端 `freeRoute`/`scoreFor`/`badgesFor` 的规则（后端 Python 重写）；
- 用 `history` 重算金额/状态，不直接信 `state.score`；
- 校验 `ending_id` 是否与路径/状态一致，不一致返回正确结局或 409；
- 加 CORS/OPTIONS；
- 在 `index.html` 里引入 adapter（前端只改一行）。

**局限：** 前端仍然掌握跳转，后端没有 session；适合演示，不适合“权威复盘”。所以它只是第 1 步。

### 5.2 正式契约（图引擎，3–5 天）

沿用 `/api/story/*` 也可以，关键是响应要包含图和结局：

```http
POST /api/story/start
-> { session_id, node, progress }

POST /api/story/answer
{ session_id, node_id, option_id }
-> { response, next_node | ending_id, ending?, score?, badges?, progress }

POST /api/story/open
{ session_id, node_id, text }
-> { intent, suggested_option_id, need_confirm, target? }

POST /api/story/confirm
{ session_id, node_id, option_id, open_text }
-> { response, next_node | ending_id, ending?, progress }

GET /api/story/review?session_id=...
-> { ending_id, title, rating, narration, next_step, score, badges, history }

POST /api/story/stop
-> { review: { status, completed, total, choices } }
```

`node` 至少返回：

```json
{
  "id": "N04",
  "title": "看似正规的证件",
  "time": "10月27日 · 微信聊天",
  "scene": "……",
  "lines": [...],
  "prompt": "……",
  "free": false,
  "presentation": {"bg": "B", "person": "alert", "phone": [...]},
  "options": [{"id": "A", "text": "……", "response": "……"}],
  "ui_option_order": ["A", "B"]
}
```

**注意：** 选项响应里不要返回 `next` 给前端做跳转，前端只认后端返回的 `next_node/ending_id`；否则又变成前端权威。

### 5.3 CORS 与兼容端点的最小改法

后端是标准库 `BaseHTTPRequestHandler`，先补预检和响应头：

```python
def do_OPTIONS(self):
    self.send_response(204)
    self._cors_headers()
    self.send_header("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
    self.send_header("Access-Control-Allow-Headers", "Content-Type")
    self.send_header("Content-Length", "0")
    self.end_headers()

def _cors_headers(self):
    origin = self.headers.get("Origin", "")
    # 演示期可回显 origin；生产建议白名单
    if origin:
        self.send_header("Access-Control-Allow-Origin", origin)
        self.send_header("Vary", "Origin")
```

并在 `_send()`/`_json()` 里也调用 `_cors_headers()`（或在 `_send` 统一加）。

兼容端点可以放在 `app.py` 的路由里，或单独 `game/compat.py`：

```python
if path == "/api/free-answer":
    # payload: {node_id, text, history, state}
    target = compat.free_answer(payload)   # "E01" 或 4
    self._json(200, {"target": target})

if path == "/api/result":
    # payload: {ending_id, score, history, state}
    result = compat.result(payload)        # {ending_id, score, badges}
    self._json(200, result)
```

兼容层只做“规则重算 + 路径校验”，不要直接 `return payload`；否则前端改 `score` 就能拿高分。

## 7. 前端也要配合的最小改动（无法完全由后端替代）

即使后端完全向前端靠，下面几项前端也必须改，否则仍然跑不起来：

1. `index.html` 引入 adapter（或在 `game.js` 内实现请求）；
2. `API_BASE` 改为同源 `/api` 或可配置地址（别写死 8000）；
3. 固定选项加 `option_id`（A/B），提交给后端；
4. `choose()` 改为 `await` 后端响应，按 `next_node`/`ending_id` 渲染；
5. 自由回答提交后处理 `need_confirm`（确认卡）或后端直接返回 `target`；
6. 结局页从 `/review` 取 `title/rating/narration/score/badges`；
7. 加 loading/error/重试；
8. 本地 `scoreFor`/`badgesFor` 降级为离线回退，不再作为权威。

如果只想“先跑起来”，兼容层只需要第 1、2 项 + 后端两个接口 + CORS；但正式版不要停在这里。

## 8. 分阶段落地（建议）

### 阶段 0：冻结与准备（0.5 天）

- 把前端 `story.js` 的 `S/E` 导出成 JSON（或人工整理成 `story_frontend_15nodes.json`）；
- 把上面的 15 节点跳转表、E15/E16 条件、N03/N15 自由规则写成测试用例；
- 明确旧七维/R 结局归档，不再作为主口径。

### 阶段 1：兼容层（1–2 天）

- 后端加 `/api/free-answer`、`/api/result`、CORS；
- 前端引入 adapter，改 API_BASE；
- 跑通 E01/E02/E04/E05/E06/E07/E08/E09/E10/E11/E12/E13/E14/E15/E16 各一条路径；
- 明确标注“演示级，路径仍由前端掌握”。

### 阶段 2：图引擎（3–5 天）

- 新配置 + `engine/scoring/sessions/schemas/validate`；
- 提前结局、自由 N03/N15、E15/E16、金额/评分/徽章；
- 16 条 E 路径 + 自由回答 + 条件分支测试；

### 阶段 3：前端切换（1–2 天）

## 9. 不要做的事

1. **不要把 E01–E16 按序号映射到 R01–P02。** 语义不同，复盘会自相矛盾。
2. **不要同时保留“七维决定结局”和“E 结局由选项跳转”。** 必须只留一套。
3. **不要继续让前端传 `score`/`state` 作为权威。** 正式版后端重算。
4. **不要要求提前结局也走完 15 步。** 前端 N03/N04/N07 等都可以直接结束。
5. **不要把 `n11_seen`/N08/N12/N13 作为 review 前置条件。** 这些是旧七维模型的要求。
6. **不要继续用旧 `validate_config.py` 的“固定 next 链”校验。** 图结构下它会误报/漏报。
7. **不要忽略 CORS/OPTIONS。** 跨域预检不通，前端根本发不出 POST。
8. **不要用 GBK 文件名重新打包前端。** 演示现场解压丢图风险很高。
